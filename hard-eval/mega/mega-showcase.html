Findings — every real issue this massive run surfaced

#FindingStatus
1–7project-tag on init · delete-by-tag · recall_fix top-K · float-rerank recall · multi-project symbol wipe · recall_fix perf · MCP-client framingFIXED
8Giant JSON data dumps ingested uncapped (1.4 GB CVE dump → 4.9 GB RAM); json is a code-grammar so it bypassed the size capFIXED — skip .json (like CSV), Advisory 4923→114 MB
9Abstention weak: returns unrelated memories at score >1.0 for never-stored queries instead of decliningOPEN — parked for grill
10recall_fix ~7.5 s at 46.6k (float-rerank union + deep ask scale with brain size)OPEN — tuning
11Writes fell to a full rebuild at scale: a single learn-fix/remember took >2 min at 46.6k. The incremental append path (O(new)) EXISTS but a too-strict precondition (all prior frames still active) meant a single tombstoned frame (dedup/supersede/delete — the mega-brain had 40) forced a full O(corpus) rebuild per write.FIXED — tolerate tombstoned priors → >2 min → 21.5 s @36.5k / 4 s @8.7k

Finding #11 was the most valuable result of the whole run — and it's now fixed. The incremental write path was always there and correct; it was being bypassed because the "is this a pure append?" check demanded every prior frame still be active, which a single tombstone (routine) broke. Relaxing it to tolerate tombstoned priors (harmless — inactive, filtered at query) restores the O(new) path: a write at 36.5k frames dropped from >2 min to 21.5 s (8.7k: 4 s). Only massive multi-project scale — where tombstones accumulate — surfaced this.
