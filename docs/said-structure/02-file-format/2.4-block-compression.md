# 2.4 — Block-compressed frames (H.265 GOP-inspired)

`.said` compresses frames in **groups** — a shared zstd block holds multiple frames under the same trained dictionary, the way an H.265 Group-of-Pictures (GOP) holds many video frames behind one reference frame. This collapses per-frame compression overhead for small chunks (paragraphs, code tokens) and lets cold-start zstd overhead amortize across dozens of frames.

## Why blocks

**Single-frame zstd** has a per-frame overhead: the compressor starts with no context, so the first few hundred bytes compress poorly. A 200-byte paragraph typically ends up 190-250 bytes compressed — worse than plain.

**Zstd with a trained dictionary** fixes cold-start: the compressor reuses a pre-trained vocabulary. But per-frame still means per-call overhead (initialization + finalization).

**Block-compressed** puts many frames in one zstd stream under the trained dict. Now:
- Setup cost amortizes across 100+ frames
- Inter-frame similarity (repeated words, phrases) compresses away
- Per-frame bytes drop to 30-60% of plaintext on realistic workloads

Typical compression ratios on SAID-ECHO's own corpus:
- Legal documents: **7-8×**
- Source code: **5-6×**
- Chat turns: **3-4×**
- Random base64 / hashes: ~1.05× (inherent limit)

## Block encoding — `ZstdDictBlock`

When a frame's encoding is `ZstdDictBlock`, the interpretation of its `FrameMeta` changes:

| Field | Standalone frame (`Zstd` / `ZstdDict`) | Block frame (`ZstdDictBlock`) |
|---|---|---|
| `offset` | byte offset of the frame's compressed bytes | byte offset of the **block's** compressed bytes |
| `compressed_len` | frame's compressed size | **block's** compressed size |
| `uncompressed_len` | frame's plaintext size | frame's plaintext size (NOT block's) |
| `checksum` | BLAKE3 of frame's compressed bytes | BLAKE3 of the **block's** compressed bytes |

The intra-block offset — where this frame sits inside the decompressed block — is stored separately in the **BLKT** section (block table), keyed by `frame.id`.

## Compressed block region layout

```
block 0
  ┌──────────────────────────────────────────────────┐
  │  zstd-compressed concatenation:                  │
  │     [ plaintext_frame_A | plaintext_frame_B |    │
  │       plaintext_frame_C | ... | plaintext_J ]    │
  │  ← compressed as a single stream using the       │
  │    trained DICT                                  │
  └──────────────────────────────────────────────────┘

block 1
  ┌──────────────────────────────────────────────────┐
  │  ... next ~256 frames ...                        │
  └──────────────────────────────────────────────────┘
...
```

Frames within a block are in write order. The BLKT maps each `frame_id → (block_index, (intra_start, intra_end))` so readers can slice into the decompressed block without re-splitting.

## Block size — the "256" convention

Default block size is **256 frames** or **400 KB plaintext** (whichever hits first). H.265 uses similar GOP sizes; the trade-off is:

- **Smaller block** → faster random access (less to decompress per frame), lower RAM footprint, worse ratio
- **Larger block** → better ratio (more inter-frame similarity), slower random access, more RAM per block

256 frames / 400 KB hits the knee in practice: compression ratio plateaus, decompress cost stays under 1 ms.

## Dictionary training

Before the first block is compressed, `compact()` trains a zstd dictionary over a random sample of the corpus:

```
compact()
  │
  ▼
if no dict exists or corpus grew > 50% since last training:
   sample frames (random 100 frames, min 100 KB total plaintext)
   train zstd dict (level 15, dict size 16-64 KB)
   store dict in DICT section
```

Trained dict is serialized in the `DICT` section and reused for all `ZstdDict` and `ZstdDictBlock` encodings. Readers must load DICT before decompressing any frame with those encodings.

## Block cache

`FrameStore::block_cache: HashMap<usize, Vec<u8>>` keeps recently-decompressed blocks in RAM. Lifetime = open file session. Eviction is currently LRU on manual calls; in production workloads the cache is rarely evicted because blocks are modest (~400 KB each) and total corpus RAM stays small.

**Hot path for repeat frame access:**
```
7 μs     — block_cache hit (memcpy from cached decompressed bytes)
~500 μs  — block_cache miss, decompress with dict
```

## When blocks are rebuilt

- **Initial `compact()`** — after ingest. Promotes all `Plain` / `Zstd` frames into `ZstdDictBlock`.
- **Re-compact** — admin action or `said compact`. Rebuilds blocks after many tombstones / deletions so reclaimed bytes aren't wasting space.
- **Never automatically after every write.** `save()` flushes pending frames as `Plain` or `ZstdDictBlock` depending on the batch; it doesn't re-partition existing blocks.

## Legal-hold + compact interaction

When `drop_tombstones` runs, tombstoned frames under `legal_hold:*` are **skipped**. Those frames keep their `ZstdDictBlock` encoding intact — the block itself is not rewritten; only frames marked Deleted get excised during a block rebuild.

This means a single block can contain Active + Tombstone + held Tombstone frames simultaneously. BLKT entries for each are preserved. Compact is careful to rebuild only blocks where ≥1 frame was actually Deleted.
