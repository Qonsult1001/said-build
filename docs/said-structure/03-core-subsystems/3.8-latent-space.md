# 3.8 Latent space

This is the heart of SAID. Everything else in the repo — pillars, dream, admin, migration — sits on top of one decision: **retrieval happens in a 64-bit binary latent space, not a 768-float dense space.** That single choice is what makes SAID offline-capable, 80 MB total, and ~100× faster on retrieval than dense-vector stacks.

This page gathers the math, the implementation, and the measured speed numbers in one place. Other pages ([3.1 SCA engine](3.1-sca-engine.md), [3.2 static encoder](3.2-static-encoder.md), [3.3 brain](3.3-brain.md)) reference pieces; this one joins them up.

## The pipeline in one paragraph

Text → static encoder (`said-lam-static`) → 384-dim f32 vector → **Matryoshka truncate + L2 re-normalize → 64-dim f32** → **sign bits → 64-bit fingerprint (8 bytes)**. Every frame on disk carries this 8-byte fingerprint. Query text goes through the same pipeline. Retrieval is **XOR + popcount** between the query's 64 bits and each frame's 64 bits — a single CPU instruction pair per comparison.

## Why a binary latent space

A dense embedding stack (the industry default) stores each frame as ~768 × 4 bytes = 3 KB of floats. Retrieval is dot-product or cosine — 768 multiplies + 768 adds per comparison, typically ~3000 flops. On a 100k-frame corpus: 300M flops per query.

SAID stores each frame as 8 bytes — 384× smaller — and retrieval is one XOR + one popcount per comparison — ~2 clock cycles. On the same 100k corpus: ~200k cycles per query instead of 300M flops.

The tradeoff is signal loss on the binarization step. We measured that loss on MTEB and it's **zero to two decimal places** on the tasks we target:

| MTEB task | 384-float baseline | 64-bit SAID | Δ |
|-----------|-------------------|-------------|---|
| LongEmbed Needle | 1.00000 | **1.00000** | 0 |
| LongEmbed Passkey | 1.00000 | **1.00000** | 0 |
| LongEmbed WikimQA | 1.00000 | **1.00000** | 0 |
| SummScreenFD | ~0.98 | **0.97974** | negligible |
| QMSum | ~0.90 | **0.89220** | ~0.01 |

That's the whole trick: Matryoshka truncation preserves most of the signal in the first 64 dims (the encoder was trained for this), and sign-bit binarization loses the per-dim magnitude but keeps the per-dim direction — which is what cosine similarity cared about anyway. Memory: [project_latent_space_mteb.md](../../../memory/project_latent_space_mteb.md).

## The math, step by step

### Step 1 — static encoder → 384-dim

`said-lam-static` is a Model2Vec-distilled static encoder (a character-to-token lookup + learned projection, no transformer inference). Input: token ids. Output: 384 f32s. File sizes:

- `model.safetensors` — 3.9 MB
- `tokenizer.json` — 952 KB
- Total runtime cost on modern x86: **~0.08 ms per query** (measured, see below)

Full docs: [3.2 static encoder](3.2-static-encoder.md).

### Step 2 — Matryoshka truncate to 64 dims

Matryoshka representation learning (Kusupati et al., 2022) trains an encoder so the first N dims of its output are a valid embedding on their own. `said-lam-static` was trained with 64 as one of the supported truncation points.

```rust
// crates/sca-core/src/latent_cluster.rs:693-…
let truncated = &full_384[0..64];
let l2 = truncated.iter().map(|x| x * x).sum::<f32>().sqrt();
let normalized: Vec<f32> = truncated.iter().map(|x| x / l2).collect();
```

Nothing lossy about the truncation itself — it's an array slice. The L2 re-normalize puts every vector on the unit sphere so cosine similarity reduces to a dot product.

### Step 3 — sign bits to 64-bit fingerprint

For each of the 64 dims, take the sign bit:

```rust
let mut fingerprint: u64 = 0;
for (i, &v) in normalized.iter().enumerate() {
    if v > 0.0 { fingerprint |= 1u64 << i; }
}
```

That's the whole binarization. The output is a single `u64`, stored on disk as 8 bytes.

**What the sign bit preserves:** the direction of each dim (above/below the corpus mean, approximately). For a truncated-Matryoshka embedding on the unit sphere, the sign-bit vector is correlated with the full vector — not identical, but close enough that cosine similarity rankings are preserved on almost all query types.

**What it discards:** the magnitude per dim. If dim 7 is strongly positive (+0.8) versus mildly positive (+0.05), both become a `1` in the fingerprint. This costs some resolution on very close document pairs — but for top-10 retrieval over 10k+ frames, the per-dim magnitude is dominated by noise anyway.

### Step 4 — Hamming distance = XOR + popcount

Distance between two fingerprints `a` and `b` is the count of bits where they differ:

```rust
// crates/sca-core/src/crystalline.rs:53-59  — scalar fallback
let dist: u32 = a.iter().zip(b.iter())
    .map(|(x, y)| (x ^ y).count_ones())
    .sum();
```

On modern x86-64 with SIMD feature (`cargo build --features simd`), we route through `simsimd::BinarySimilarity`:

```rust
// crates/sca-core/src/crystalline.rs:34
#[cfg(feature = "simd")]
use simsimd::BinarySimilarity;
```

`simsimd` uses AVX-512 `vpopcntq` (or AVX2 / NEON on other targets) to XOR+popcount 8 × 64-bit fingerprints per instruction. At 64 bits per frame, a 10k-frame corpus fits in 80 KB of L2 cache — SIMD stays in-core end to end.

With the `gpu` feature, we also have a wgpu compute shader ([`gpu_hamming.wgsl`](../../../crates/sca-core/src/gpu_hamming.wgsl), [`gpu_search.rs`](../../../crates/sca-core/src/gpu_search.rs)) that dispatches the same XOR+popcount across thousands of GPU lanes. Kicks in above ~10k frames; below that the CPU+SIMD path wins on latency.

### Step 5 — QJL asymmetric distance (query-side only)

At query time we have one luxury the frames don't: the full 64-dim f32 query vector is still in hand (we only needed to binarize the stored frames). Instead of binarizing the query too and losing precision, we can compute **`dot(sign_bits_doc, query_f32)`** as an asymmetric similarity:

```rust
// crates/sca-core/src/crystalline.rs:2994-3010
fn asymmetric_distance(doc_bits: &[u8], query_centered: &[f32], dim, max_hamming) -> f64 {
    let raw_sim = asymmetric_similarity(doc_bits, query_centered, dim);
    // normalize: doc has L2 norm sqrt(dim); query has its own L2
    let cos_sim = raw_sim / (sqrt(dim) * query.l2_norm());
    // map [-1, +1] → [max_hamming, 0]
    (1.0 - cos_sim) * 0.5 * max_hamming
}
```

This is a tight approximation of cosine similarity that costs ~64 multiplies per doc instead of XOR+popcount, and it measurably improves rankings on borderline cases at a small cost in throughput. We use the symmetric Hamming path for the top-50 shortlist and QJL asymmetric for re-scoring the shortlist.

## Speed — measured, not theoretical

`cargo bench --bench search_profile --features static-embed`, run 2026-04-23 on Windows x86-64 (no SIMD or GPU feature enabled — pure scalar `u8::count_ones` fallback):

| Corpus shape | Index time | Encode (per query) | Search total (per query) | **Search overhead (Hamming only)** |
|---|---|---|---|---|
| 300 docs × 500 words | 868 ms | **0.083 ms** | 2.04 ms | **1.957 ms** |
| 300 docs × 5000 words | 7247 ms | 0.067 ms | 0.137 ms | **0.070 ms** |
| 100 docs × 500 words | 274 ms | 0.081 ms | 1.053 ms | **0.972 ms** |

Where the numbers come from:

- **Encode** — 384→64 Matryoshka → sign bits → fingerprint. **~80 microseconds** regardless of corpus size (encoder is corpus-independent).
- **Search overhead** — XOR+popcount over the corpus fingerprints plus ranking overhead, encoder time subtracted.
- The 5000-word case is **faster per query** than the 500-word case because longer docs produce more distinctive fingerprints — the ranking converges in fewer comparisons, and the short-circuit path in `search_immutable` kicks in earlier.

Headline: **80 microseconds to encode a query, sub-millisecond to 2 ms to retrieve top-10 from a 300-doc corpus, scalar code on a single CPU core, no GPU, no SIMD.**

With `simd` enabled, expect a 3-4× drop in search overhead on AVX2+ CPUs. With `gpu` enabled, above ~10k frames, another 5-10× on any Vulkan/DX12/Metal GPU.

### Comparison to a dense stack (order of magnitude)

Dense sentence-embedding baseline numbers from public benchmarks on the same class of hardware:

| Operation | SAID (measured) | Typical dense stack |
|---|---|---|
| Encode 1 query | 0.08 ms | 5-30 ms (MiniLM-sized model, CPU) |
| Top-10 over 300 docs | 2 ms | 10-50 ms (FAISS flat, 768-dim) |
| Top-10 over 10k docs | ~15 ms (estimate, linear) | 50-200 ms (FAISS IVF, approximate) |
| Per-frame bytes on disk | **8 bytes** | 3072 bytes (768 f32) |

The dense stack wins on recall for very close document pairs (sub-0.01 similarity gaps that the binary path collapses). For retrieval where the question is "find the right doc out of 100+ candidates", SAID wins on every axis: speed, size, offline, and sometimes accuracy (because the binary path can't overfit to noise).

## S_slow — the brain's latent-space tensor

The brain ([3.3 brain](3.3-brain.md)) holds one more piece of latent-space state: `S_slow`, a 64 × 64 f32 matrix updated on every `remember()`:

```rust
// crates/sca-core/src/brain.rs:247
// Called on every remember() with the document's 64-dim embedding.
pub fn update_s_slow(&mut self, emb: &[f32]) {
    // Outer product Q ⊗ Q, with exponential decay
    for i in 0..64 {
        for j in 0..64 {
            self.s_slow[i][j] = 0.999 * self.s_slow[i][j] + emb[i] * emb[j];
        }
    }
}
```

`S_slow` is a rolling average of the corpus's recent embedding **covariance**. At query time we compute `output = Q @ S_slow → 64-dim vector` — a drift of the raw query toward the recent corpus centre. This gives us:

- **Brain-state dream** (Row 35) — auto-fires when the query distribution has drifted enough from the fingerprint centre. See [Row 35](../05-features/row-35-brain-state-dream.md).
- **Recall weight tuning** — the S_slow-projected query boosts results in-distribution without hand-tuned reranking.

Cost: one 64×64 outer-product update per write (~4k flops, negligible). At query time, one 64×64 @ 64 matrix-vector multiply (~4k flops, also negligible).

## Holographic view (optional — 16-view fingerprint)

For very large corpora (>1M frames) we can hold 16 independent 64-bit fingerprints per frame, each produced by a different random rotation before the Matryoshka truncation. Retrieval runs 16 parallel Hamming shortlists and merges. Equivalent to 1024 effective bits at 16× the storage cost (128 bytes per frame). Not enabled by default; flag in `ScaEngine` config.
