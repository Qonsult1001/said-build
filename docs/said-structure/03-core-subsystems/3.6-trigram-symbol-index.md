# 3.6 — Trigram + symbol index

Two independent indices that make `.said` fast at lexical retrieval. Both built at ingest/compact, both serialized into their own sections (`TRGM`, `SYMS`), both live in memory via mmap at read time.

## Trigram inverted index

**What it is.** For every overlapping 3-gram in the corpus, a posting list of frame indices that contain it. Turns substring search (`said grep`) from O(N × L) scan into O(L + postings) lookup.

**Where the code is.** [`crates/sca-core/src/trigram_index.rs`](../../../crates/sca-core/src/trigram_index.rs).

**How it's used.**
1. `brain.grep("Eleanor")` → lowercase → 3-grams `["ele", "leo", "eon", "ono", "nor"]`
2. For each trigram, read its posting list (Vec of frame indices)
3. Intersect posting lists → candidate frames
4. Verify substring match against the full text of each candidate (fixes false positives from rare 3-gram collisions)
5. Return ranked results

**Cost.**
- Build: ~100 ms per 10k frames (one-off at compact)
- Query: typically sub-millisecond for rare substrings, few ms for very common ones

**Storage.**
- In-memory: roughly 5-15 bytes per unique trigram × average-posting-length
- On-disk: zstd-compressed serialization, typically ~5-8% of the corpus text size

**Serialization.** Section `TRGM` in the `.said` file. Layout: `TRGM` magic | u32 doc_ids_count | per doc_id (u16 len + utf8 bytes) | u32 uncompressed_len | u32 compressed_len | zstd bytes. See [2.2 Sections](../02-file-format/2.2-sections.md#trgm-trigram-inverted-index).

## Symbol index

**What it is.** Exact symbol-name lookup for code frames. Populates `said sym <name>` queries with fully-qualified location data (kind, start line, end line).

**Where the code is.** [`crates/sca-core/src/symbol_index.rs`](../../../crates/sca-core/src/symbol_index.rs).

**Recording flow.** During `said init <dir>` (see [code plugin](../06-ingestion-plugins/code.md)):

1. Tree-sitter AST-chunks a source file
2. For each chunk, call `SaidFile::record_symbol(name, doc_id, kind, start_line, end_line)`
3. At compact time, `rebuild_trigram_index()` consumes the pending symbols and builds `SymbolIndex`
4. `SymbolIndex::serialize_raw()` goes into the `SYMS` section

**Query flow.** `brain.sym("FrameStore", max=5)`:

1. Look up "FrameStore" in the symbol name → positions map
2. Each position is a `(doc_index, kind, start_line, end_line)` tuple
3. Translate `doc_index` back to `doc_id` via `trigram_doc_ids` (the same list as TRGM)
4. Build `SymbolResult { name, doc_id, kind, start_line, end_line }` for each hit

**Performance.** Sub-millisecond on any corpus. Not parameterized by corpus size — pure HashMap lookup.

**Supported languages.** (Via tree-sitter grammars; see [code plugin](../06-ingestion-plugins/code.md)):
- Rust, Python, JavaScript, TypeScript, Go, Java, C#

**Symbol kinds.** `fn`, `struct`, `enum`, `trait`, `impl`, `class`, `method`, `type`, `const`, `?`

## How the ask router uses both

`said ask` / MCP `ask` runs the 3-engine fusion. Symbol and grep engines use these indices:

```
Engine A — Sym (confidence 1.00)
    For each symbol-candidate spelling generated from the query
    (snake_case, camelCase, PascalCase joins, raw lowercased / original-case):
        brain.sym(candidate, max=5).iter().filter(|hit| hit.name == candidate)

Engine B — Grep (confidence 0.40 – 0.95)
    For each query keyword ≥ 3 chars:
        brain.grep(keyword, 30).iter()
            .filter(|hit| terms_present(hit.content) >= min_terms)
```

Engine C (SCA semantic) is independent — see [3.5 retrieval pipeline](3.5-retrieval-pipeline.md).

## Shared doc_id ordering — `trigram_doc_ids`

Both indices use positional `doc_index` values into a shared `Vec<String>` called `trigram_doc_ids`. The list is the exact frame order at the moment the trigram index was built.

Implications:
- SYMS serialization is smaller (u16 indices vs variable-length doc_ids)
- After any frame add/remove that invalidates the ordering, the indices must be rebuilt
- `FrameStore::compact()` triggers `rebuild_trigram_index()` to keep them synced
