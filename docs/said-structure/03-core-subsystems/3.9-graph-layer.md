# 3.9 Graph layer

SAID does have a graph. It isn't a pre-materialized knowledge graph like Cognee's or Neo4j's — it's a **retrieval-time entity graph** reconstructed on every query from frame tags + fingerprint similarity + co-occurrence. This page documents what exists today so `said ask "who does Alice work with"` stops feeling like magic.

Not to be confused with **tree-sitter** ([3.2 static encoder](3.2-static-encoder.md), [06-ingestion-plugins/code.md](../06-ingestion-plugins/code.md)), which is the AST parser we use to chunk **code files** at ingest. Tree-sitter produces *syntax trees inside a single file* and is done after chunking. The graph layer below is a different thing entirely: *cross-frame semantic edges* consulted at query time.

## What the graph is

- **Nodes** — every Active frame in the brain. One frame = one node.
- **Edges** — all implicit. Two frames share an edge if they share one or more of:
  - A **speaker** tag (`speaker:alice`)
  - An **entity** tag (`entity:SF`, `entity:Acme`)
  - A **foreign-key** tag (`fk:users.id`, set by the SQL docs plugin)
  - A **module** tag (`module:card`)
  - A **source** file (`source:src/auth.rs`)
  - Near-identical fingerprints (Hamming distance below a threshold — implicit semantic edge)
  - A co-occurrence of the same capitalised entity phrase in frame content

No edge is stored on disk as such. The graph is **reconstructed on demand** from tags, fingerprints, and content scans.

## When it fires

Only when a query **needs** multi-hop reasoning. The fast path ([3.5 retrieval pipeline](3.5-retrieval-pipeline.md)) is:

1. Layers 1-5 — SCA fingerprint top-50 + trigram + BM25 + entity-speaker boost + hyphen-asymmetric retrieval
2. **Layer 6 — iterative multi-hop bridge** (the graph) — fires only if the top-1 / top-2 score gap is narrow (< 1.5), i.e. the brain isn't sure which doc answers the query
3. Layer 7 — phrase tiebreaker on the final top-10

Most queries never reach Layer 6. Queries like `"who did Alice work with"` or `"what paper did the author of X cite"` — where the direct answer doesn't live in any single frame — do.

## Layer 6 in detail — how the graph walk works

From [`recall.rs:682-816`](../../../crates/sca-core/src/recall.rs#L682-L816):

### Step 1 — detect whether we need a graph hop

```rust
if reranked.len() >= 2 {
    let gap = reranked[0].1 - reranked[1].1;
    if gap < 1.5 {
        // ambiguous — graph walk will help
    }
}
```

If the top answer is 1.5× better than the runner-up, we trust the direct answer and skip the walk. Otherwise the query is "ambiguous" in the fingerprint space — exactly the signal that a bridge hop would disambiguate.

### Step 2 — extract query entities + relational context

Query entities are capitalised multi-word runs (`Hermann, Prince Of Hohenlohe`), detected with a small particle allow-list (`of / the / de / von / van / du / la / le / el / al / bin / ibn / di / and / on / in`).

Relational-context words are detected against a shortlist — today: `born / died / buried / nationality / award / studied / mother / father / grandmother / place of birth / place of death`. These are the LoCoMo- and WikimQA-derived words that most often signal a multi-hop question.

### Step 3 — extract bridge entities from the top-3 doc texts

Walk each top-3 doc's sentences. For every sentence that mentions either a query entity OR a relational-context word, pull **every capitalised entity from that sentence** that isn't already in the query. A stopword list strips grammatical lead-ins (`The / This / That / His / Her / He / She / They / Their / After / Before / However / Although / During / Between`).

The output is up to **5 bridge entities**, sorted longest-first (longer entity names are more specific, so the re-query is more targeted).

### Step 4 — re-query with each bridge

For each bridge entity, re-issue the query as `"<bridge> <relational context>"`:

```
// original query: "where did Hermann die"
// top-3 docs mention: "Hermann, Prince Of Hohenlohe was born in 1768 in Langenburg"
// bridge entity: "Langenburg"
// re-query: "Langenburg died"
```

The re-query runs through the full SCA engine — its own top-10 results come back with SCA scores.

### Step 5 — merge bridge results with original ranking

Bridge hits boost the original ranking with a weight of `0.4 × max_sca`. Bridge hits that aren't in the original top-50 get added with a floor of `0.7 × max_sca + 0.4 × (bridge_score / max_bridge)`. The set is re-sorted.

### Step 6 — Layer 7 phrase tiebreaker

If two frames still tie after the bridge walk, 2-6-gram content-word phrase overlap picks the winner.

## What the graph is good at

- **Multi-hop factual** — `WikimQA`-style questions where the answer is `A → B → C` and no single frame has both `A` and `C`. Scored 1.0 on WikimQA; the graph is the reason.
- **Entity-scoped conversation recall** — `"what did Alice say about Bob"` finds frames where Alice spoke, re-queries for Bob-mentioning frames, blends.
- **FK-linked SQL retrieval** — foreign-key-tagged frames get co-walked when a module refers to a shared hub table. Used by `said snapshot` to decide Exclusive vs Shared classification.

## What it isn't good at — honest list

- **Exhaustive enumeration.** `"list every company Alice has worked at"` — if one of those companies is in a low-SCA-score frame that never enters the top-3, we miss it. Cognee's pre-materialised triples don't.
- **Typed relations.** Our edges have no predicate. You can't filter on `relation_type = employs` or `relation_type = located_in` because there's no relation type — just co-occurrence. Zep's temporal KG does this natively.
- **Cheap at scale.** Layer 6 re-encodes + re-searches once per bridge entity. At 100k-frame + Layer 6 firing on 30% of queries, this becomes measurable. A pre-indexed graph would be cheaper per query.
- **Structured graph queries.** Cypher / SPARQL / Gremlin-style traversals are not possible; the graph doesn't exist on disk to traverse.
- **Cross-brain reasoning.** Edges only exist within a single `.said`. Two brains can share a schema (via `said snapshot`'s lens) but not a graph.

## Relation to Cognee, Zep, Hindsight

| System | Graph style | Build cost | Query cost | Exhaustive? | Typed? |
|---|---|---|---|---|---|
| **SAID** (today) | retrieval-time reconstruction | 0 (implicit) | O(3 docs × 5 bridges × encode+search) per ambiguous query | No | No |
| **Cognee** | pre-materialised KG | LLM-per-ingest triple extraction | O(graph traversal) | Yes | Yes |
| **Zep / Graphiti** | pre-materialised temporal KG | LLM-per-message extraction | O(graph + time filter) | Yes | Yes + time-typed |
| **Hindsight** | 4-network hybrid | precomputed | multi-net fusion | Partial | Partial |

**Takeaway**: for the ~80% of queries where multi-hop is one-step-away and the bridge is findable in the top-3 docs, SAID's implicit graph matches the pre-materialised systems. For the other 20% — exhaustive enumeration, typed-relation filtering, very-large-corpus traversal — it doesn't, and an opt-in `said build-graph` pass is on the roadmap.

## Extension path (roadmap preview)

A future [`said build-graph`](../12-roadmap.md) post-ingest command will:

1. Run a local entity + relation extractor (heuristic first, BYO-LLM plug-in second) over every frame.
2. Emit typed triples as `Semantic` frames with tags `subject:X`, `relation:R`, `object:Y`, `kg_edge:true`.
3. Persist a per-brain edge index (new section alongside TRGM/SYMS) so graph queries are O(index lookup).
4. Keep the retrieval-time walker as the default; promote the pre-built graph only when `kg_edge:true` frames exist.

Opt-in, so brains that don't need it don't pay the build cost.
