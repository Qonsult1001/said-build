# 14.15 — Canon memory (the 80/20 split, stored once, rendered per language)

The highest-leverage form of `.said`'s owned memory: store the **80% framework canon** — the byte-identical
*shape* that repeats across every entity/project — **once, language-neutral**, and at recall **guide the
LLM to render it in the active language**, so the agent regenerates the 80% for free and authors only the
20% delta. One canon → every language. Not a per-language/per-architecture catalogue.

## SHIPPED (core + CLI + MCP). Public name = "blueprint"; "canon" is the internal design term.

"canon" is not a recognized dev term (research: devs say pattern/template/blueprint; "canonical" = a
normalized data form). So the USER-FACING surface is **blueprint** — a known dev word for a reusable
plan you build from. `canon` stays only in these design notes.

Built + tested as the second learning channel alongside learn-fix (learn-fix = the specific 20%,
blueprint = the reusable 80%), mirroring the coding-fix engine (same Procedural store, same fusion
scorer, same SAID_RECALL_LANG/PROJECT hard-filters) with ONE deliberate rule change:

- **KEEP-FIRST dedup** — `learn_blueprint` of an existing SHAPE is a no-op (the original stands), unlike
  learn-fix where the latest verified solution supersedes. Identity = shape folded with SAID_PROJECT,
  doc_id = `shape::<blake3-16>`.
- **promote** (`learn_blueprint --promote` / MCP `promote=true`) — the explicit "make this my new
  standard": supersede (the learn-from-edit lever; the deliberate exception to keep-first).

Surfaces (all call the ONE shared `sca_core::ask` writer/reader, byte-identical):
- core: `learn_blueprint` / `promote_blueprint` / `recall_blueprints` (`crates/sca-core/src/ask.rs`);
  tests `crates/sca-core/tests/test_blueprint.rs` (3 GREEN: round-trip + keep-first, promote, project isolation).
- CLI: `said learn-blueprint --shape <s> --sections <json> [--lang] [--label] [--promote]`,
  `said recall-blueprint --shape <s> [--min-similarity]`.
- MCP: `learn_blueprint` / `recall_blueprint` tools; proven live `hard-eval/blueprint_mcp_e2e.js` (8/8 PASS
  as a separate JSON-RPC process).
- steering: `MCP_INSTRUCTIONS` + `SKILL_BODY` name both tools ("recall_blueprint before building a repeated
  shape, render in the active language, write only the 20%").

NOTE — a latent whole-CLI Windows bug surfaced + fixed while adding subcommands: the clap-derive help
builder for the large command enum overflowed the 1MB main-thread stack; `main()` now runs on an 8MB
worker thread.

## Two learning channels, same loop: learn-fix (the 20%) + canon (the 80%)

`.said` now learns at BOTH scales of code, with the same learn-from-edit promote loop:
- **learn-fix** = learning on the **20% (the specific fix)**: "when you hit THIS error in THIS spot, THIS
  is the fix" (episodic, problem -> solution).
- **canon** = learning on the **80% (the reusable structure)**: "a Create endpoint always has these 6
  sections -- reuse them, don't recreate" (procedural, shape -> template).
Complementary, both inside `.said`, both promoted on a gated user edit (see learn-from-edit below).

## How it triggers (rides the EXISTING steering hooks -- doc 16, built + proven live)

Canon is NOT a separate `node said-canon-tool.js` process (that script is throwaway prototype scaffolding;
in the product the canon, the section hashes, and the commands all live INSIDE `.said` as native CLI/MCP).
The promote/heads-up surfaces through the SAME hook channel learn-fix recall already uses:

| Trigger | When | How `.said` knows what changed |
|---|---|---|
| PostToolUse hook (Edit/Write) | the moment the agent edits a file | new section content vs the section hash `.said` stored when it generated it (blake3, the `said.log.md`/in-`.said` baseline) -- a changed GENERATED hash = the signal |
| SessionStart / next run | start of next session | re-scan tracked files, compare to stored hashes -- catches edits the hook missed (manual edits, other tools) |

Both are complementary: the hook catches it live; the scan is the catch-up backstop. "Before vs after" is
answered by the hash `.said` saved at generation time (before) vs on-disk content (after) -- no separate
process, no external state.

CRITICAL (doc 16, proven live A/B): the promote question must surface as PLAIN FACTS on the trusted
`UserPromptSubmit` channel -- NOT as an imperative on the tool-output channel (Claude flags that as
prompt-injection and refuses it). So "make this your new standard?" rides the same factual-framing slot as
recall and session-resume, gated by the existing `confirm`/bypass.

## Harvest-at-init: auto-learn blueprints from an existing repo (SHIPPED)

Onboarding `.said` onto an existing codebase shouldn't require an agent to hand-author every blueprint —
`said harvest <dir>` (CLI), `harvest_blueprints` (MCP) scans the repo and learns blueprints from the
structures that ALREADY repeat. Grounded in code-clone / idiom-mining research (NiCad, Wrangler,
source-code pattern mining): a structure is a reusable pattern only at **minimum support = 2** (the
universal clone-class default — a pattern must repeat), above a **size floor**, under a **similarity
gate** (~0.70 == clone detection's "dissimilarity <= 30%"). One-offs are skipped (high precision, low
noise; matches the 80/20 "repeats across entities" definition). Thresholds are named, documented constants
(`MIN_SUPPORT` / `MIN_SKELETON_STEPS` / `SIM_GATE`), never magic numbers.

Mechanism (`crates/sca-core/src/harvest.rs`, reuses existing machinery — no new parser): `ast_chunk`
gives each function's call-skeleton (what it DOES, step by step); functions are bucketed by leading-verb
shape + clustered by Jaccard skeleton similarity; each cluster of >=2 yields ONE blueprint whose sections
are the COMMON ordered skeleton. Structural + deterministic (no encoder needed to cluster).
`learn_blueprint(verified=false)` => KEEP-FIRST, so re-running harvest/init never clobbers a hand-tuned or
promoted blueprint. Proven on real repos: sca-core/src (42 files, ~1012 fns -> ~11 blueprints: new 5x,
from 3x, doc 3x...) and the OrchestrationFactory C# app (93 files, 1117 fns -> enforce 5x, logic 3x,
get/wire/call/sdk/llm...). Tests: `crates/sca-core/tests/test_harvest.rs` (repeated-only + keep-first
re-run); live MCP `hard-eval/blueprint_harvest_e2e.js`.

## The idea (from the said-cgp-cs 80/20 split)

Real codebases are ~80% **framework canon** + ~20% **entity-specific content**
(`SAID-ECHO/said-cgp-cs/docs/80-20-split.md`). For a `Create<Entity>` endpoint the 80% — request
signature, audit pipeline, error-envelope CATCH, the OPENJSON shred *pattern*, the response wrap — is
identical across Account / BinSponsor / 3DSecure / your-next-app. Only 6 slots change (the fields, the
DML, the children, the response projection, the business guards). A `calculate-interest` function is the
same: the *scaffold* around it (validate → compute → guard → return) recurs; only the formula is new.

**`.said` should remember the 80%, not just past fixes.** Then every new entity costs the agent only the
20% — the 80% is never re-derived or re-tokenized.

## Why NOT a per-language catalogue (the owner's constraint)

`said-cgp-cs` stores the canon per `(architecture × host × language)` — a real catalogue. That does not
scale to "global portable memory." `.said` must do it the way it already does fix-recall: store the
**learning/intent ONCE** and **guide the engine** to the right concrete answer for whatever language is
active — exactly how `recall_fix` stores the invariant (not the per-language diff) and `SAID_RECALL_LANG`
guides to the active language.

## The representation — decided by research (structured NL, not a formal IR)

Research is decisive on what an LLM renders reliably across languages:

- **No universal formal IR exists** — *"natural language consistently emerges as the most effective
  intermediate representation across all target languages; no universally effective intermediate formal
  language exists"* ([Assessing Code Generation with Intermediate Languages, arXiv:2407.05411]). ⇒ a
  formal IR is the WRONG canon format.
- **Structured natural language beats pseudocode** — decompose into ordered *phases* in NL, then render
  ([Structured Chain-of-Thought Prompting, TOSEM 2025]). ⇒ canon = ordered NL phases.
- **Model-authored specs render most reliably** — let the LLM phrase the canon in its own vocabulary
  ([Self-Spec, OpenReview 6pr7BUGkLp]). ⇒ don't impose a rigid schema it fights.

So a **canon frame** is language-neutral structured intent:

```
shape:   Create<Entity>            # the intent key — fingerprinted, like recall_fix's action residue
phases:  (ordered structured NL — the 80%)
  1. validate the request body is present
  2. shred the input fields from the request payload
  3. guard required fields → error envelope on missing
  4. write the primary row (the DML)
  5. write child rows if any
  6. project the response object (and wrap/return per the framework envelope)
slots:   [fields, dml-target, children, response-shape, business-rules]   # the 20%, named
guide:   render in the ACTIVE language/architecture; keep phase order; fill slots from the entity schema
```

## Recall = the existing engine, pointed at structure

This needs **no new retrieval mechanism** — it reuses what's proven:

| `recall_fix` (live) | canon recall |
|---|---|
| stores the invariant, not per-language code | stores the canon (phases+slots), not per-language code |
| intent/action fingerprint keys recall | the `shape` (Create/Update/GetById/Paginate/SubResource) is the intent key |
| `SAID_RECALL_LANG` guides to the active language | the active stack guides the LLM to render the canon there |
| LLM adapts, gate verifies | LLM renders the 80% + fills the 20%, gate verifies |

So: agent asks "Create endpoint for Invoice in `<stack>`" → `.said` recalls the **Create canon** (one,
global) → LLM renders the 80% in the target language and fills the 6 slots from Invoice's schema. The 80%
is regenerated from one stored canon, never re-tokenized.

## Competitive position (evidenced, not marketing)

Read the real READMEs/specs of 7 agent-memory systems in `SAID-ECHO/research` (mem0, LEANN, MemPalace,
Memvid, Claude-Context, GBrain, Chonkie). EVERY one does **retrieval** — find existing facts / chunks /
code — and **none does generative structural reuse** (harvest a code shape → store as a portable blueprint
→ render it in a NEW language). LEANN does AST-aware *chunking for search*; GBrain's `skillify` is *static*
workflow markdown — closest, but not cross-language code structure. Verdict: **procedural memory is becoming
a standard category, but "harvest structural canon → recall → cross-language render, in one portable
BYO-LLM file" is genuinely differentiated** — conditional on blueprint extraction + render QUALITY holding
(see the recall-ranking limit below). Honest claim: the capability, not "world-first memory system."

## Known limit — recall RANKING on short skeletons is the encoder, not the scorer

Harvested blueprints with short implementation-token skeletons rank-separate poorly: a generically-central
shape can out-rank the right one (the embedding "right neighborhood, wrong item" problem). This is NOT a
blueprint-scorer bug — `best_blueprints` is byte-identical to the proven `best_coding_fixes` (14.15
mandate: recall reuses the existing engine, no new mechanism). It is the **static Model2Vec encoder's
isotropy on short code**, already diagnosed + solved in `SAID-ECHO/research/MinishLab`:
`diff_failures.md`/`baseline_results.md` show the exact symptom (candidates collapsing to one confidence);
`code_encoder_compare.md` shows **`potion-code-16M` ranks the correct item #1 where the text encoder ranks
>10**; `02_semhash.md` adds a 5-signal rerank (definition boost etc., NDCG@10 0.854 ≈ 137M at 11× speed)
that breaks near-ties but is query-class dependent. FIX PATH: adopt the code encoder + semble rerank in the
SHARED engine, measured on a real brain — not a blueprint-only divergence. What works TODAY: harvest,
exact-shape recall, cross-language render, the 80/20 token saving, learnings/auto-update. Only fuzzy
cross-shape RANKING waits on the encoder.

## Why this is the moat (and frictionless)

- **Structural reuse, not lexical** — `Create` is `Create` across entities, projects, AND languages; the
  canon is reused every time that shape recurs, forever. This is the real 80/20 token story (skip
  re-emitting 80% of every file in every bundle), far bigger than "recall one function."
- **Owned, portable, compounding** — the canon set is `.said`'s asset; it grows as the agent verifies new
  shapes; it travels across models/machines as one file. A competitor can copy retrieval; they can't copy
  your accumulated canon.
- **Frictionless / not an obstacle** — `.said` is the canon layer *underneath* Claude/Kimi/Cursor: the
  host agent just gets a better, cheaper, more consistent answer (80% handed over; it spends tokens only
  on the 20%). `.said` makes the agent better, which is why they buy it instead of routing around it.

## Canon acquisition — born TWO ways (forward + harvested), dedup-by-shape

Canon enters the brain through two paths, so an existing `.said` + a fresh `init` is immediately
canon-rich instead of starting empty:

1. **Forward (as we work):** after a verified build, the agent records the canon for a shape it just
   implemented — same trigger as `learn_fix` on green.
2. **Harvested at `init` (retroactive):** when a project is `init`'d into an existing brain, `.said` reads
   ALL the existing code, detects recurring structural shapes (Create/Update/GetById/handler/…), and
   extracts a canon from the patterns already there. The codebase you already have becomes canon on day
   one — the 80% you've written a hundred times is captured automatically.

**Dedup by SHAPE (not by text):** if a canon for that shape already exists, **skip it and move on** — do
NOT store a second. The first canon for `Create` stands; later occurrences only *reinforce* it (recall
weight), they don't duplicate. This keeps the canon set small and authoritative (one canon per shape),
and is why harvesting a big existing codebase doesn't bloat the brain — N Create endpoints → ONE Create
canon. (Contrast `learn_fix`'s per-task identity; canon identity is the SHAPE alone.)

This is the best-of-both-worlds the owner asked for: new projects grow canon forward, and importing
existing code mines canon retroactively, with dedup keeping it to one-per-shape.

## Prototype result (2026-06-28) — thesis PROVEN + one design fix found

Prototyped on the live CLI (canon stored via the `learn_coding_fix` engine, tagged `canon:create`):
- **Store + recall by intent:** the canon (6 NL phases + named slots) stores and recalls; shape-phrased
  queries score 0.59–0.65 and the bare action "create" recalls at 0.61 via the action-residue fingerprint.
  **Recall-key finding:** canon must be keyed on the SHAPE/ACTION, not the entity noun — a distant
  noun-led paraphrase ("Invoice endpoint") scored only 0.18. An agent naturally queries by action
  ("create endpoint"), and storing the canon's problem as the bare shape makes this robust.
- **ONE canon → TWO languages (the headline, proven in physical code):** the same stored canon rendered
  into `dotnet` (`InvoiceController.cs`) and `rust/axum` (`invoice.rs`) — identical 6-phase 80% structure
  (accept → guard → INSERT → project), only the 20% slots (fields/DML/response) differ per language.
- **DEDUP FINDING (must fix for canon):** storing a 2nd Create kept the frame count flat (good, no
  pile-up) — BUT it did so by **last-write-wins supersede**, which OVERWROTE the good canon with the
  throwaway. Canon's rule is the OPPOSITE: **keep the existing canon, SKIP the new** ("if canon exists,
  don't dedup, move on"). So canon needs a **keep-first** dedup (first canon for a shape stands; later
  occurrences only reinforce recall-weight), NOT `learn_fix`'s supersede. This is the one engine change
  canon requires beyond the existing store.

## Marker convention v2 — header index + provenance classes (the "intent-driven, less-noise" fix)

Refinement (owner): intent-driven development should have FEWER inline comments but a RICHER header — a
`@said-managed` **section index** (OKF/wiki-style) so each region is referenced by a NUMBER, not verbose
per-line comments. Plus a marker for **where the AI added NEW code**, which makes a real metric possible:
*how much new code did the AI generate vs the framework/old system?*

Research backing: ~41% of code merged globally in 2025 was AI-assisted but carries **no structured
provenance record** ([nhimg.org/code-provenance]); the field's problem is **fragmentation** — "can't query
across repos because every repo uses a different schema or none" ([same]). There is **no dominant
numbered/indexed managed-region standard** (closest: `#region`, MDA/EMF protected regions, source-gen
marker attrs — all language-specific). So `.said` can define the ONE consistent, **language-agnostic,
indexed** convention the field lacks — which is exactly the "global" property canon needs (same markers in
C#, Rust, SQL, TS…).

**Header section index (declared ONCE; the body uses terse numbered anchors):**

```
// @said-managed: index  canon=Create<Entity>  lang=dotnet
//  §1 accept-and-audit   Fully    framework
//  §2 guards             Ignore   entity-20%
//  §3 dml                Ignore   entity-20%
//  §4 response           Ignore   entity-20%
//  §5 envelope+return    Fully    framework
// @said-managed: end
```
Body regions then collapse to `// §2` … `// §end` — no prose, just the indexed anchor (clean code,
trivial to recall/manage, and the index is the OKF-wiki for the file).

**Provenance classes (extends the said-cgp-cs Fully/Ignore with AI/Human):**

| Class | Meaning | Counts as |
|---|---|---|
| `Fully`  | framework canon, regenerated byte-identical | **framework** (free — `.said` regenerated it) |
| `Ignore` | entity-specific slot, agent/human fills, preserved on re-render | **entity 20%** |
| `AI`     | NET-NEW code the AI authored (not canon, not a slot) | **AI-net-new** |
| `Human`  | hand-edited outside any slot | **human** |

**The calculation it unlocks (the buy-worthy metric):** count lines per class →
`framework% / entity-slot% / AI-net-new% / human%`. So you can state, auditable:
> "Old system: human wrote 100%. With `.said` canon: framework regenerated **X%** for free; the AI authored
> only **Y%** net-new; the human touched **Z%**." — a real productivity + token-savings number, and the
> active code-provenance record the industry currently lacks. (Reference renders updated in
> `hard-eval/canon-proto/`.)

## Convention v2 fixes (rendering, ordering, global OKF map)

Three corrections from real use:

1. **ASCII anchors, not `§`.** The section sign `§` is U+00A7 (non-ASCII) and renders as mojibake across
   editors/terminals/OSes — fatal for a GLOBAL standard. Anchors are now pure ASCII `S1..SN` (body) +
   `index` block. All canon artifacts are verified **0 non-ASCII bytes**.
2. **`SN` = EXECUTION ORDER.** The earlier index listed sections in a static order the body didn't follow
   (the AI net-new block ran before the guards, but was numbered last). Anchors now match the body
   top-to-bottom, so the header index IS the file's flow map. Header carries
   `NOTE: SN = EXECUTION ORDER`.
3. **OKF reserved files = the GLOBAL map** (Google Open Knowledge Format: `index.md` catalog + `log.md`
   history; markdown + YAML frontmatter; only `type` required). `said.index.md` catalogs EVERY managed
   section across EVERY file as `file#SN`, so audit/recall map back globally — this is the "wiki that maps
   to files" the owner asked for and the cross-repo audit the provenance research says is missing.
   `said.log.md` is the change/provenance history. (Demo: `hard-eval/canon-proto/said.index.md` + `.log.md`.)

**The honest metric framing (owner's correction):** the framework 80% (`Fully`) was **AI-authored ONCE**;
its ongoing cost is ~0 because it's regenerated byte-identical. So the value is two distinct things:
- **Token savings** = the `Fully` regions re-emitted for free on every file/entity, forever (no re-reasoning).
- **The genuine hard work** = the `AI` net-new + `Ignore` entity-20% the agent must actually think through.
The OKF catalog makes this auditable per file: "X of N regions regenerated free; Y of N are the real work."

## Labels = EDIT-SAFETY (greenfield) + PROVENANCE (only when scanning old code)

The owner caught a real confusion: in a FRESH build the AI writes EVERYTHING, so "AI-added vs your code"
is meaningless there. The industry-proven model (Speakeasy custom code regions: "the generator OWNS
generated files; editing them is overwritten on the next run; custom regions are carried forward") labels
by **edit-safety**, not authorship. Two separate axes, used per scenario:

**Axis 1 -- EDIT-SAFETY (ALWAYS shown; the only thing a user must know to act):**

| Label | Meaning | What the user does |
|---|---|---|
| **GENERATED** | `.said` regenerates this; your edits get OVERWRITTEN | Don't edit here. To change it: edit the **canon/template** (updates everywhere), or **`said eject <Sn>`** to take ownership (it becomes YOURS). |
| **YOURS** | `.said` PRESERVES this across renders | Edit freely; carried forward (Speakeasy custom-region contract = said-cgp-cs `@said-managed: Ignore`). |

So "how do I control a GENERATED/LOCKED section?" -> don't fight it in the file; **edit the canon or
eject**. That answers the owner's control question.

**Axis 2 -- PROVENANCE (shown ONLY for scanned/brownfield code):** when `.said` ingests an EXISTING
codebase it CAN tell what was already there from what it added, so review is meaningful:
**WAS-YOURS** (pre-existing) vs **SAID-ADDED** (new -- review this). In greenfield this is omitted (all
AI; not useful) -- only edit-safety shows. The owner's "everything is AI / what about scanned old code"
question = exactly this: greenfield shows edit-safety; brownfield adds WAS-YOURS/SAID-ADDED for review.

**Control commands (the user's levers over GENERATED code):** `said eject <Sn>` (GENERATED -> YOURS);
edit the **canon** (one change updates every GENERATED instance); `said diff` (brownfield: WAS-YOURS vs
SAID-ADDED). Demonstrated labels in `hard-eval/canon-proto/` (greenfield: GENERATED/YOURS only).

## Output discipline (audited against writing-great-skills)

The emitted markers/wiki are held to the same rules as a skill (predictability, single source of truth,
no duplication, no-ops cut, leading words, progressive disclosure). Audit of the first render caught real
violations, now fixed:
- **Duplication (was 3x):** section name + class appeared in the code header index, every body tag, AND
  the wiki table. FIX: the full index + the how-to-edit legend live in ONE place -- `said.index.md`
  (the progressive-disclosure target). The code header is 2 lines + a pointer to it.
- **No-ops (was per-line):** every GENERATED body tag re-explained "(do not edit; said eject…)". FIX:
  body tags are now **anchor + ONE leading word** (`// [S3] guards  YOURS`) -- the word IS the
  instruction; GENERATED/YOURS are leading words defined once.
- **Co-location:** all control guidance (eject / edit-canon / diff) sits under one heading in the wiki,
  not scattered across the file.
This is a build rule for the canon emitter, not just this demo: **the markers carry the anchor + one
leading word; the legend, the map, and the controls live once, in `said.index.md`.**

## The REAL question: an edit is FEEDBACK -- does the canon learn from it? (the moat)

Re-anchored on the aim (owner): canon exists to REUSE a known pattern so the AI doesn't recreate what it
already has -- and the real question is NOT "did the user lose work," it's: **when a user edits a generated
function because they prefer a different way, does the canon LEARN that (so every future entity uses their
way) or keep generating the old way?**

This is the fork between a static template and a LEARNING canon -- and the learning version is the moat
(it's `.said`'s "memory that improves from how you work" thesis: `learn_fix`/reconsolidation, applied to
structure). Research backs both halves: capture user corrections as the highest-signal feedback, feed them
back to evolve the template -- but PROMOTE deliberately, never auto (auto-learn pollutes; our own
`moat-edge-and-pollution-findings` scar).

**Decision -- the canon learns, on a gated PROMOTE:** when a user makes a meaningful edit to a GENERATED
section, `.said` asks:
> "You changed how `Create` works. Make this your new standard (update the canon -> every future Create
> uses your way), or just this once?"
- **New standard** -> the canon updates; the user's preferred way propagates to every future entity. They
  stop re-fixing the same thing. THIS is the moat: the canon improves from how you actually code.
- **Just this once** -> the edit stays local; canon unchanged.
- Gated (the existing `confirm`/bypass) so a throwaway hack can't silently become the standard -- the
  anti-pollution guard. Dedup still keep-first on the SHAPE; promotion is the explicit way the first
  canon evolves.

So the prompt that matters is NOT "keep/discard your edit" (loss-protection -- a non-problem; see below)
but **"promote your edit to the standard?"** (feedback -> canon learning). That is the feature.

## Edit conflicts -- DON'T build a merge UI; lean on diff + git (decision)

Owner's question: "do we care if a user changed a GENERATED section -- keep or restore -- as long as it
works? How do Claude/Cursor deal with it; isn't inline keep/reject the easier part?" Researched it, and
the answer simplifies our design:
- **Cursor:** accept/reject controls on every change -- the EDITOR's diff UI is the keep/reject.
- **Claude Code:** has no diff UI; "reviewing changes means running `git diff`" -- GIT is the safety net.
- **Neither builds a custom "keep my edit vs regenerate" merge dialog.** It is not a thing the standard
  tools do -- so `.said` shouldn't either. The 3-way interactive prompt (prototyped) was OVER-ENGINEERING.

**Decision -- the simpler, standard-matching model:**
1. On regenerate, `.said` writes the file via the normal edit path; the host (Cursor/IDE/`git diff`)
   shows the change as a DIFF and the user keeps/rejects with the tools they already use. `.said` does NOT
   own a merge UI.
2. **Git is the safety net** -- an overwrite is recoverable via `git diff`/revert. No custom prompt needed.
3. The ONE thing `.said` uniquely does (and Cursor/Claude cannot): **regeneration respects the
   `@said-managed` markers -- it rewrites only GENERATED sections and leaves YOURS sections byte-for-byte
   untouched.** That marker-scoped regeneration IS our value; the keep/reject is the host's job.

So the drift "prompt" is at most a one-line WARNING ("`.said` will rebuild GENERATED sections; YOURS are
kept -- review the diff"), gated by the existing `confirm`/bypass. The interactive keep/discard/eject menu
is retired in favor of the host's diff + git. (`said eject` stays as an explicit command for "make this
GENERATED section mine permanently" -- a deliberate one-off, not a per-rebuild prompt.)

## Plain-English model (what a USER sees vs the internal terms)

The internal terms (`canon`, `eject`, `overwrite`) are jargon a user shouldn't have to learn. Grounding:
- **canon** = the saved TEMPLATE `.said` generates a GENERATED section from (like a Word template). It
  lives IN `.said`. User-facing word: "the saved template / what .said auto-generates".
- A GENERATED section is rebuilt from that template; a YOURS section is your code, never touched.

So the drift prompt is shown ONLY when you hand-edited a GENERATED (auto-generated) section and a rebuild
would lose it. User-facing wording (no jargon):
- **Keep my change** -- stop auto-generating just that one section (internally: keep, skip regen).
- **Discard my change** -- restore the generated version (internally: overwrite from canon).
- **Take ownership** -- the section becomes yours forever; `.said` never regenerates it (internally: eject).

`canon`/`eject`/`overwrite` remain ONLY in these design notes + code internals; users see plain words.

## Wiki upkeep + drift guard (prototyped + tested)

Two gaps the owner caught, both prototyped in `hard-eval/canon-proto/said-canon-tool.js`:

**Wiki is AUTO-MAINTAINED, library drill-down.** `said.index.md`/`said.log.md` must NOT be hand-kept (they
go stale the moment a 2nd file is added). The tool SCANS all canon files and regenerates both, with
project -> file -> section drill-down (project totals; per-file `[link](file) -- N sections (Y YOURS / G
GENERATED)`; per-file section table). Add a file, re-run, it's indexed. `said.log.md` stores each section's
hash (the drift baseline). Controls legend stated ONCE (single source of truth).

**GENERATED-edit drift guard (prompt unless bypass).** A GENERATED section the user hand-edits would be
silently overwritten on regenerate. The guard compares the on-disk section hash to the last-rendered hash
in `said.log.md` (the industry checksum-drift method); on mismatch:
- **bypass set (Claude permission standard)** -> overwrite silently;
- **else** -> PROMPT: `[k]eep your version / [o]verwrite with canon / [e]ject (make it YOURS)`.
Only GENERATED sections can conflict (YOURS is preserved anyway). Tested: clean=safe, edited=prompt,
edited+bypass=silent. Aligns to the existing `confirm:true` gate pattern (MCP destructive tools).
