# 14.14 — Byte-exact tombstone restore with BLAKE3-chained audit

## Plain-English

When a frame is superseded or deleted, its full compressed content is **retained** in the brain through a two-step tombstone lifecycle. The user can restore any prior version by `doc_id` and get back the **byte-identical original**, cryptographically verified. A BLAKE3-chained audit log proves no intermediate tampering occurred. This is an enterprise-compliance primitive (M365 Recycle Bin + legal-archive + SOX audit trail) that **no shipping memory system — mem0, Zep, Cognee, Dume, LEANN, Mem.ai, Hindsight, MemoryLake, usecortex — offers.**

This is not compression magic. The content survived in the brain's block section through the version lifecycle. The audit log and hash chain are what make the restore **provably correct**, not merely best-effort.

## Formal statement

Let $D$ be the original document bytes and $F$ its `.said` frame.

**Frame state machine:**

$$F \in \texttt{Active}, \texttt{Tombstone}, \texttt{Deleted}$$

**Lifecycle:**

- On `put_with(doc_id, D)`: $F \leftarrow \texttt{Active}$. Stores compressed zstd(D), BLAKE3(D), fingerprint, meta.
- On update with same `doc_id`: prior $F \leftarrow \texttt{Tombstone}$, new $F' \leftarrow \texttt{Active}$. **Compressed content of prior F is untouched.**
- On `delete` or retention-sweep: $F \leftarrow \texttt{Deleted}$. **Compressed content still untouched.**
- On `compact`: every frame with status $\texttt{Deleted}$ AND no `legal_hold:`* tag gets its compressed payload **physically reclaimed** from the BLKT section. Status removed from frame index.

**Restore guarantee.** For any frame $F$ with status $\in \texttt{Tombstone}, \texttt{Deleted}$ that has not been reclaimed by `compact`:

$$\operatorname{adminrestore}(docid) \Rightarrow \operatorname{decompress}(F.\text{content}) = D \text{and} \text{BLAKE3}(\operatorname{decompress}(F.\text{content})) = F.\text{hash}.$$

Byte-identity of the restored content is verified by hash match. Any mismatch raises an error and refuses the restore.

**Audit chain.** Every mutating operation — `put_with`, `mark_frame_deleted`, `admin_tombstone_records`, `admin_restore_tombstoned`, `admin_add_legal_hold`, `admin_release_legal_hold`, `compact` — appends one entry to the AUDT section:

$$\text{chainhash}*n = \text{BLAKE3}\big(\text{chainhash}*{n-1}  n  \text{ts}  \text{actor}  \text{kind}  \text{target}  \text{detail}\big).$$

To verify: walk the chain, confirm each entry's hash equals the recomputation. Break point is localised: `said admin audit --verify` reports the first broken entry.

## Proof sketch

**Claim (retention invariant).** For any frame with status $\in \texttt{Tombstone}, \texttt{Deleted}$, the frame's compressed block is not removed from the BLKT section until a `compact` call with matching retention policy has run.

*Sketch:* `mark_frame_deleted` sets `status` field only; it does not touch BLKT. `drop_tombstones` and `drop_tombstones_keep` skip any frame carrying a `legal_hold:`* tag. `compact` walks the BLKT section, copies forward every block whose frames contain at least one non-Deleted reference; blocks with zero live references are physically dropped. Therefore content survives until a compact run with permission to reclaim it — never before.

**Claim (byte-identity on restore).** For a restored frame, $\operatorname{decompress}(F.\text{content}) = D$ with probability 1 under a correct zstd implementation, and is verified post-hoc by hash match.

*Sketch:* zstd is a lossless compression codec. `admin_restore_tombstoned` does not modify $F.\text{content}$; it only flips `status` from `Tombstone` back to `Active`. The byte sequence stored at ingest is the byte sequence returned on restore. BLAKE3 hash match (stored at ingest, verified at restore) provides cryptographic confirmation of byte-identity.

**Claim (tamper evidence).** If any actor modifies any AUDT entry between two mutations, chain verification fails at the modified entry or the one immediately after.

*Sketch:* BLAKE3 is collision-resistant. Each entry's hash depends on all prior hashes. Altering byte $k$ of entry $n$ changes chain hash $n$, which is verified against entry $n+1$'s `chain_hash` field. Mismatch detected in O(chain length).

## What this is NOT

**Not compression magic.** A 60 MB document is stored as ~20 MB of zstd-compressed bytes at level 3, or ~15 MB at level 19 (see [3.4 FrameStore](../03-core-subsystems/3.4-framestore.md) for actual observed ratios). Restore decompresses the stored 15-20 MB back to 60 MB. It does NOT restore 60 MB from 64 bits or from the BLAKE3 hash alone — that's information-theoretically impossible.

**Not fingerprint-based reconstruction.** The 64-bit fingerprint is used for retrieval only (see [14.1 QJL asymmetric](14.1-qjl-asymmetric.md), [14.8 Matryoshka sign-bit](14.8-matryoshka-signbit.md)). It is not a lossy compression of content. It cannot reconstruct anything.

**The value proposition is retention + verification**, not reconstruction. The content survived on disk; the audit chain proves nobody tampered with the retention. Stating this honestly is what makes the claim publishable.

## Measured impact (what it protects against in benchmarks)

This mechanism isn't tested by MTEB or LoCoMo — it's not a retrieval-quality feature. It's protected by **chamber tests** in [10-benchmarks/chambers.md](../10-benchmarks/chambers.md):

- **Restore round-trip chamber**: delete → tombstone → restore produces byte-for-byte content-hash match. Passing since the admin CLI shipped.
- **Legal-hold blocks retention chamber**: `legal-hold-add doc_X CASE-A` followed by a retention sweep with `--older-than-days 0` leaves `doc_X` intact. Passing since legal-hold shipped.
- **Audit chain break detection chamber**: flip one byte in an AUDT entry; `audit --verify` exits non-zero and names the first broken entry. Passing since the BLAKE3 chain shipped.
- **Admin retention-sweep chamber**: sweeps respect `--older-than-days` and `--keep-per-doc` while honoring legal holds. Passing.

Four chambers, 4/4 passing. These are the primary defense against regression on this feature.

- **Related**: M365 Recycle Bin (Microsoft), AWS S3 versioning + object lock, Commvault / Veeam enterprise backup, WORM storage (Write-Once-Read-Many) compliance archives, blockchain-based audit logs (certificate transparency, Merkle trees over append-only logs).

These are file-system / database-level features imported into the memory-system layer. That import is the novelty.
- **Distinctly different from enterprise backup systems**: those operate at the file or VM level, not at the frame-of-memory level. SAID lets you `admin restore doc_id memo --version 3` with byte-exact guarantee. Commvault lets you restore a file. Different granularity, different audience.
- **Publishable claim**: byte-exact restore of prior memory-frame versions with BLAKE3-chained audit trail and legal-hold-aware retention sweep, available at `.said` frame granularity, is a **first-of-class capability in the memory-system category**. Enterprise-compliance-ready (GDPR right-to-erasure, SOX audit-trail, HIPAA retention, legal-hold-on-discovery) out of the box.

## Known limitations

- **Once `compact` reclaims a Deleted frame, restore is no longer possible.** This is by design — the whole point of compact is reclaiming storage. But it means retention policy is critical: an overeager `retention-sweep --older-than-days 30` followed by `compact` **can** lose content forever. Enterprise policy recommendation: `--keep-per-doc 1` as the default; legal holds for active compliance matters.
- **AUDT chain verifies in-file integrity, not file-swap attacks.** An adversary who can replace the whole `.said` file with a different one defeats the in-file audit chain trivially. Out-of-file attestation (signing the head hash with an OS keychain / HSM / remote signer on every save) is the mitigation and lives on the [roadmap](../12-roadmap.md#admin--audit) as "External attestation."
- **Chamber tests are our only automated verification.** No formal model-checking proof. Fine for a v1 shipping feature; on the roadmap to tighten if customers ask.
- **Compression ratio is workload-dependent.** Natural-language text: 2-3× at level 3, 3-4× at level 15. Code: 3-5×. Binary / already-compressed content: 1-1.1×. Restore latency scales with compressed size, not original — matters for large frames but is sub-second for anything under ~100 MB.

## The competitive framing

This is the retention-and-verification moat, not a compression moat. When positioning SAID against:

- **Mem0 / Zep / Cognee**: they have no prior-version retention at all. A memory update loses the old memory. SAID keeps it + proves it.
- **Enterprise backup systems**: they work at file or VM level. SAID works at frame-of-memory granularity.
- **Blockchain / append-only logs**: those solve integrity. SAID adds the byte-exact restore + legal-hold + retention sweep in one place.

Phrase the pitch as: *"Every memory version is retained, every mutation is cryptographically logged, every restore is byte-verifiable, and legal holds are first-class. No other memory system in the field has this."* That statement is defensible today with shipped code.
